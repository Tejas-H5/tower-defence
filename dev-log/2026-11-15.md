# 2026-11-15 - Lines and grids

As I'm now finally getting around to optimising the physics code, I realise that I built the wrong thing (kind of).
I built `spatial_grid_rect_iterate`, and I guess that isn't really so wrong, but actually the physics isn't doing 
that many rect queries - it is mainly doing a line query:

```odin

the_physics_code_for_bullets_more_or_less :: proc() {
	for i in 0..< bullet_pool.count {
		ray := Line{pool.items[i].position_prev, pool.items[i]._position}
		for i in 0..< state.enemies.count {
			other_rect := get_rect(&state.enemies, i)
			res := line_intersects_rect(ray, other_rect)
			if res.num_hits > 0 {
				set_entity_position(state, pool, i, res.hits[0].pos)
			}
		}
	}
}
```

The bullets move quickly, so I've modeled them as a ray + rectangle.
Right now, the physics engine will actually collide every enemy with the ray,
in an attempt to find the 'first' enemy we're colliding with, and then 'fix'
the collision by moving the bullet back to that enemy.
Subsequent code can then do a rectangle query to find all the enemeis a bullet is intersecting with.

It just now occurs to me that a side-effect of this, is that a bullet cannot pierce through multiple enemies
	within a single frame - at least, not without some extra code.
We could have a `can_pierce` boolean that disables this code, then the subsequent collision code can do 
	a rect query AND a line query to collide items.

Anyway, I've now built `spatial_grid_line_iterate` to accelerate line queries, and this seems like the correct thing to do.
Funnily enough, I was able to make use of `spatial_grid_rect_iterate` in it's implementaiton!
Pure coincidence that this worked out in the end.

The idea is that our physics code now puts the objects into a grid cell. 
When we do a line query, rather than looping over every object, we just want to loop over the 
grid cells that the line overlaps with (think about the laser weapons in Faster Than Light).
We effectively need to iterate all the points along a line that intersect with the grid. 
I've broken this logic out into `grid_line_intersection_iterator` so I can test it properly.
It boils down to this: 
- given the current position, and the direction of the line, grid-snap this point's x coordinate or y coordinate to the line
- figure out which change in `x` or `y` moves us further along the line itself.
	- The line can be parameterised as `line start` + `t` * `line direction`. Since these are Vec2s, this actually gives us 2 equations.
		by fixing `pos.x = a gridsnapped value`, we can compute `t` as `(pos.x - line start.x) / direction.x`. Same for `y`.
- continue doing this till you run out of line

There's an additional catch - a line may pass very close to the corner of a grid square, without
actually overlapping it, but it may still be colliding with items in that near-missed cell!
It turns out to be simpler than I thought - remember the `spatial_grid_rect_iterate` that was 'incorrect' from earlier?
Rather than iterating all the cells at the intersection point, we just do a rectangle query at that intersection point - 
	the rectangle would be about the size of whatever the maximum radius of an entity is, as that is how much 
	of it would be sticking outside it's grid cell that could potentially collide with our line.
