# 2026-11-18 - The spatial grid

The actual spatial grid I implemented initially was a static size hashmap with a doubly 
linked list inside it. 
This is actually the first time implementing a bespoke datastructure like this and I
wanted to see if I even had the skill to do it at all (Raddbg has been a godsend).

Some other alternatives I considered but then discarded:
- Normal odin hashmap `map[Vec2i][dynamic]int` - this is what I would usually do but I decided
	I wanted to see if I could do it this other way where I allocate all my memory upfront and
	use a fixed-memory approach. I can change it to this later. I wouldn't be too
	surprised if it were faster
- Counting sort
	- The Google AI suggested that I can use counting sort (??) to a) count how many items will be in each cell,
		and then b) insert the exact right number of items into those cells. 
	This seemed pretty interesting, but I didn't understand how this approach handled collisions, and
	I don't think this approach really took advantage of the fact that items can remain in the same cell 
	for many frames and therefore don't really need to do a full reset between frames.
- Bounding volume heirarchy using rectanges or circles (BVH)
	- This seems quite complicated to implement. I may try this another time
- Quad Tree
	- same as BVH

It was shaped like this:

```odin
// This is the main structure where everything will go in.
// It's basically a hashmap with a doubly-linked list inside it.
Spatial_Grid :: struct($N: uint) {
	items:     [N]Spatial_Grid_Item,
	grid_size: f32,
	max_entity_radius: f32,
	count:     int,

	//...
}

Spatial_Grid_Item :: struct {
	first: ^Spatial_Grid_Handle,
	last:  ^Spatial_Grid_Handle,

	grid_coord: Grid_Coord,
	// Used to dedupe slots when we're iterating all grid x line intersections.
	visited:    bool,
}

Spatial_Grid_Handle :: struct {
	// `handle` indexes into the main data. Also it's 1-based for ZII. 
	// It's the only way we can tell if a value is present or not - the grid coord isn't
	// enough because 0, 0 is also a valid grid coord.
	handle: int, 
	// The pool this thing is a part of. if Spatial_Grid_Item had a $T parameter, this would be a part of it.
	pool: rawptr,

	item: ^Spatial_Grid_Item,
	next: ^Spatial_Grid_Handle,
	prev: ^Spatial_Grid_Handle,
}

```

`Spatial_Grid_Item` was a 'head' node in the hashmap, and `Spatial_Grid_Handle` was a node or a slot in the hashmap.
`Spatial_Grid_Handle` would live directly on the entities themself!
`visited` is really only used on the `first` item in the linked list chain so it's kinda a waste when
	multiple items are in the same cell (this is foreshadowing).
I got a bunch of tests working, but it never worked in practice!
Though it was a bit of a noob mistake, it was kind of hard to pin down.
The main error came down to this bit of code:

```odin
cleanup_code_in_a_nutshell :: proc() {
	// Clean up dead entities, add new entities
	for i := 0; i < pool.count; i += 1 {
		if pool.items[i].health <= 0 || pool.items[i].lifetime_timer < 0 {
			spatial_grid_remove(&game.spatial_grid, &pool.items[i].spatial_grid_handle)
			pool_unordered_remove(pool, i)
			i -= 1
		}
	}
}
```

See, I was smart - I did the unordered remove _after_ I remove it from the spatial grid, so that
`spatial_grid_remove` does not get a bunch of zeros!
Except - there is an extremely subtle bug here.
`pool_unordered_remove` works by moving `pool.items[pool.count - 1]` to `pool.items[i]`, and
then decrementing the pool count by 1. 
This keeps removals O(1) BUT it means our entities no longer occupy stable positions. 
This turns out to be a problem with our `Spatial_Grid_Handle` - the `Spatial_Grid` was
actually written assuming that `Spatial_Grid_Handle` were stable!

Stabilising it is simpler than I thought. 
I updated the sparse grid to look like this :

```odin
Spatial_Grid :: struct($N: uint) {
	items:   [N]Spatial_Grid_Item,
	slots:   [N]Spatial_Grid_Slot, // Stable memory for our items
	grid_size: f32,
	max_entity_radius: f32,
	count:     int,

	//...
}

Spatial_Grid_Item :: struct {
	first: ^Spatial_Grid_Slot,
	last:  ^Spatial_Grid_Slot,

	grid_coord: Grid_Coord,

	// Used to dedupe slots when we're iterating all grid x line intersections.
	visited:    bool,
}

// This may not be a stable reference
Spatial_Grid_Handle :: struct {
	// Should never be nil. This will be a stable reference.
	slot: ^Spatial_Grid_Slot,
}

```

Now, `Spatial_Grid_Handle` can be moved around freely and all our internal code just needs to deal with
	`Spatial_Grid_Slot`.
The interface can stay the same. 
My `spatial_grid_add_or_update` can be updated to just set the handle's slot if it ever sees that it's nil:

```odin

spatial_grid_add_or_update :: proc(
	g: ^Spatial_Grid($N),
	handle: ^Spatial_Grid_Handle,
	pos: Vec2,
	radius: f32,
	idx: int,
	pool: rawptr,
) {
	if handle.slot == nil {
		handle.slot = __spatial_grid_new_slot(g)
	}

	//...
}
```

The `spatial_grid_remove` proc can be updated similarly.
Surprisingly, that was pretty much it (other than some variable renaming).
`visited` is now on `Spatial_Grid_Item` instead of the handle directly.
Our datastructure is basically a classical hashmap with open-addressing and linked lists 
for collisions.
And it looks like it works! Mostly...
