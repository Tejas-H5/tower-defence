I currently use `closest_entity_SLOWWW` to get each gun to pick the closest enemy, and shoot at that enemy:

```odin
closest_entity_SLOWWW :: proc(pool: ^Item_Pool(Entity), pos: Vec2, max_range: f32) -> (int, bool) {
	target : int = -1
	min_dist : f32 = max_range
	for i in 0..<pool.count {
		dist := linalg.length(pool.items[i]._position - pos)
		if dist < min_dist {
			min_dist = dist
			target = i
		}
	}
	return target, target != -1
}
```

Works trivially when there are 1000 objects, not so good when there are 100,000. (soon there will be 1,000,000 objects 
apparently, which idot added this to the roadmap).
As a function of the number of enemies, and the number of towers, computing the target for every gun would be O(enemies * towers).

Can we do any better?
Some ideas:
- We can give guns a maximum range, and only shoot things when they are in range of a gun
    - Can't do this, because I want my guns to be very long range
- Can we accelerate this lookup with one of those acceleration data structures?
    - Actually now that I think about it, we can - if we use a bounding volume heirarchy to store our entities, we can     
        accelerate distance queries, not just overlap queries... 
        - For those not familiar: a BVH would be a tree where each node is a simple shape like a circle or rectangle 
            that contains a bunch of other nodes, the leaves being actual objects.
            If the nodes were circles, it would make sense that they can speed up queries like 'which object is closest to this point/line/whatever?'
            - I just don't know how to build it is all.
        We'll consider rewriting our physics to use a BVH later, since it keeps coming up.
    - We can also do a spiral search using a spatial grid. I.e you start at a point, chec the grid squares around that one,
        check the grid squares around those ones, you're spiraling the outside of your point.
        It would also be more optimal to use a circular shape for this traversal.
        You can stop as soon as you find the first item.
        A perfectly balanced bvh can narrow 1,000,000 objects in `log2(1000000) ~= 20` 20 iterations.
        The spiral search is technically unbounded - it assumes all your objects are already kinda close together
        so it doesn't matter.
        - Rather than doing a spiral search, if the grid is sparse enough, you can just iterate every
            single one assuming your hash table supports directly iterating the keys. 
            This is no longer infinitely bounded like the spiral search.

It turns out there's a way to improve the targeting performance just by making a change to it's logic.
Usually this kind of 'sidestepping' the problem is a cop-out, but I'll allow it this time because we would
    probably have to make this kind of change anyway:

- Instead of each tower computing the logic from the enemeis to the tower, they 
    can compute the distance from the enemies to the base that they're guarding. 
    - This not only makes more logical sense, but also means I just need to compute distances once and then allocate them to the 
        guns later. 
        - Typical min heap problem if you know you know. I'll just be using an array though ngl
            - Odin has `core:container/priority_queue`. Bro thought of everything
        - This also lets the towers be more coordinated - i.e right now they could all fire at the same guy which is a 
            bit of a waste, but now some central thing is allocating targets to them
            - Establishing this coordination is just going to be how the gameplay works by default,
                but you could imagine a game where the towers are decentralized by default, and
                getting them to coordinate involes linking them somehow by placing down more connecting/comms items
            - There is currently a second issue where a gun fires so fast that it might target an enemy that is
                currently alive, but would have been killed by the previous shot so it would have been
                more optimal to move it's target to another enemy in the meantime.
                This will not solve that problem.

For now I'll go with the targeting logic update, since I want to do that regardless of whatever
